# Command: recur trait

Manage trait configuration in `.recur/config.toml`.

`recur trait` is the first-class interface for reading and writing per-project
behavior policies (traits) that tune how commands like `trace-id`, `trace`, and
`find` operate.  Traits are stored under the `[traits.*]` sections of the
project-local `.recur/config.toml` file created by `recur init`.

It also discovers capability traits: Warp, watch, merge, Git, and proposed unmerge.
Their preference/notes fields describe project intent only; unlike consumed runtime
policies, they do not enable/disable commands or authorize execution. See
[Capability traits](main.command.trait.capabilities.readme.md).

## Subcommands

```
recur trait list                          # Configured traits plus built-in capabilities
recur trait explain <name>                # Explain commands, status and effective metadata
recur trait get <key>                     # Get a trait value
recur trait set <key> <value>             # Set a trait value
```

## Key Format

Keys use dot-path notation.  The `traits.` prefix is optional:

```
trace_id.enabled
trace_id.producer_keywords
traversal_budget.max_depth
traversal_budget.depth_guard
stdin.exclude_missing
content_search.max_file_bytes
```

## Examples

```bash
# Show all trait sections
recur trait list

# Get a single value
recur trait get trace_id.enabled
recur trait get traits.traversal_budget.max_depth

# Set keyword overrides for trace-id role classification
recur trait set trace_id.producer_keywords "publish,send,dispatch"
recur trait set trace_id.consumer_keywords "subscribe,queuebind,receive"
recur trait set trace_id.trigger_keywords  "register(,route,map"

# Tune traversal budget
recur trait set traversal_budget.max_depth  3
recur trait set traversal_budget.depth_guard clamp

# Disable trace-id policy overrides (not a universal capability switch)
recur trait set trace_id.enabled false

# JSON output
recur trait list --json
recur trait get trace_id.enabled --json
```

## How It Relates to Other Commands

| Trait section             | Command(s) that consume it         |
|---------------------------|------------------------------------|
| `[traits.trace_id]`       | `recur trace-id`                   |
| `[traits.traversal_budget]` | `recur trace`, `recur trace-id`, `recur trace-stats` |
| `[traits.stdin]`          | all commands with `--stdin`        |
| `[traits.content_search]` | `recur find`, `recur id`, `recur callers`, `recur callees` |
| `[traits.separator_merge]`| `recur merge`                      |

## Workflow

```bash
# 1. Initialize config (creates .recur/config.toml with all trait defaults)
recur init

# 2. Inspect current traits
recur trait list

# 3. Override for this project
recur trait set trace_id.producer_keywords "publish,send,dispatch"

# 4. Verify the change
recur trait get trace_id.producer_keywords

# 5. Run trace-id — it picks up the custom keywords automatically
recur trace-id "ulu.topic.dot.ownership.create" --scope "**" --ext .cs
```

## Separation of Concerns

- `recur init` — scaffolds `.recur/config.toml` with sensible defaults
- `recur trait` — reads and writes specific values in that config
- Commands (`trace-id`, `trace`, etc.) — consume the config at runtime

`recur trait` does NOT modify command behavior directly.  It only edits the
config file.  The consuming command picks up changes on the next invocation.
Capability preferences have no runtime consumer: they remain descriptive metadata.
List/get/explain read the nearest ancestor config and provide built-in capability
defaults without creating files; set requires an existing config.
