# Core Improvement 15: `unflatten` Command and Recomposition Profiles

**Status:** Future Vision (Long-Distance Backlog, Not Active)  
**Priority:** Very High  
**Category:** Data Recomposition, Animation Pipelines, Unix Composition

## Vision

Add a first-class `recur unflatten` command that reconstructs structured output from flattened entries (`path`, `value`, `kind`) with a selectable output target (`text`, `json`, `xml`, etc.).

This closes the loop:

1. `flatten` (decompose)
2. transform/merge (compose and edit)
3. `unflatten` (recompose)

The core principle is to keep output format behavior in separate profile files so content and formatting can evolve independently.

## Why This Matters

Today, `flatten` exists and is already useful for pipelines. But the reverse direction is missing as a native command.

Current gap:

- `recur flatten` emits rich records (`path`, optional `value`, `kind`).
- `recur merge` can ingest flattened JSON but currently reconstructs path-only trees and does not preserve `value`/`kind`.
- Complex recomposition is possible with shell tools, but requires too much glue code for common workflows.

`unflatten` should make those pipelines native, predictable, and short.

## Command Goal

Make this possible with minimal shell glue:

```bash
recur flatten input.yaml --json \
  | recur merge --stdin --base config \
  | recur unflatten --stdin --format yaml
```

And for ASCII animation workflows:

```bash
recur merge frame.layers.json --base mug --json \
  | recur unflatten --stdin --format text --profile formats/ascii-water.json
```

## Proposed CLI Surface (Draft)

```text
recur unflatten [INPUT] [OPTIONS]

OPTIONS:
  --stdin                     Read flattened records from stdin
  --format <text|json|xml|yaml|toml|csv>
  --profile <FILE>            Output profile file (repeatable; later overrides earlier)
  --root <PATH>               Optional root path to materialize
  --strict                    Fail on collisions/invalid hierarchy
  --on-conflict <error|last-wins|first-wins|array>
  --sort <path|input>         Reconstruction order policy
  --output <FILE>             Write rendered output to file
  --frames                    Treat selected path set as frame sequence
  --frame-key <PATH>          Frame grouping key/path prefix
  --dry-run                   Validate and print reconstruction plan only
```

Notes:

- `--format` controls the output target.
- `--profile` defines rendering behavior and can be layered.
- Global `--sep` should continue to control hierarchy separator interpretation.

## Canonical Input Model

`unflatten` accepts arrays of objects in the same shape generated by `flatten --json`:

```json
[
  { "path": "config.db.host", "value": "localhost", "kind": "text" },
  { "path": "config.db.port", "value": "5432", "kind": "text" },
  { "path": "server@host", "value": "localhost", "kind": "attribute" }
]
```

Supported path primitives:

- Segment separator (default `.` unless overridden by `--sep`)
- Array index tokens like `[0]`
- Attribute tokens like `@name`

## Recomposition Profiles (Key Design)

Profiles are files, separate from scene/data files, so teams can iterate independently.

### Layered Profile Model

Use a profile stack where later files override earlier files:

1. Core base profile
2. Medium/output family profile
3. Domain profile (for example: config, ascii-scene, api-schema)
4. Variant profile (for example: water, lager, stout)
5. Runtime CLI overrides

### Example Profile

```json
{
  "version": 1,
  "extends": [
    "formats/base.core.json",
    "formats/base.text.json"
  ],
  "output": {
    "format": "text",
    "newline": "\n",
    "trim_trailing_whitespace": true
  },
  "render": {
    "transparent_token": "#",
    "token_map": {
      ".": ".",
      "_": "_",
      "-": "-"
    }
  },
  "frames": {
    "enabled": true,
    "group_by": "frame",
    "order": "numeric",
    "hold_ms": 90
  }
}
```

This allows shared bases across many outputs and small override files per scenario.

## Integration With Existing Commands

### Minimum interoperability contract

For full round-trip pipelines, `merge` and `unflatten` must preserve and consume:

- `path`
- `value`
- `kind`

### Recommended merge extension

Add a flat-aware mode for merge outputs:

```text
recur merge ... --format flat
```

Where output shape remains a list of flat records rather than a path-only file tree.

This avoids losing semantic data before `unflatten`.

## Phased Implementation Plan

### Phase 1: Core `unflatten` MVP

- Input: flattened JSON records
- Output: `text` and `json`
- Features: `--stdin`, `--format`, `--strict`, conflict policy
- Tests: deterministic ordering and collision handling

### Phase 2: Structured format targets

- Add `xml`, `yaml`, `toml`, `csv` emitters
- Add array and attribute fidelity rules
- Add round-trip test suites (`flatten -> unflatten`)

### Phase 3: Profile system

- Add `--profile` layering with deterministic precedence
- Add validation for unknown profile keys
- Add profile fixtures for common use cases

### Phase 4: Frame and animation support

- Add `--frames` and `--frame-key`
- Emit frame streams for text rendering pipelines
- Make ASCII demo pipelines depend primarily on recur commands

### Phase 5: Merge/Unflatten native pairing

- Add `recur merge --format flat`
- Preserve `value`/`kind` across merge operations
- Reduce shell dependency in demo pipelines to orchestration only

## Success Criteria

- Lossless round-trip for supported formats in standard cases.
- `flatten` + `merge` + `unflatten` can run as a native recur pipeline.
- Profile layering supports shared bases and narrow overrides.
- Demo animation workflows (ASCII mug with sparkle frames) run with mostly recur commands.
- Behavior is deterministic and script-friendly.

## Non-Goals (for this improvement)

- Direct raster image compositing (PNG/JPEG pixel operations) in v1.
- Replacing all shell tools; shell remains orchestration glue.
- Solving all schema/type semantics in first release.

## Risks and Mitigations

- Risk: conflicting paths during recomposition.  
  Mitigation: explicit `--on-conflict` policy plus `--strict`.

- Risk: format-specific edge cases (XML attributes, mixed content, CSV typing).  
  Mitigation: phased emitters and dedicated round-trip fixtures.

- Risk: profile sprawl.  
  Mitigation: layered profile hierarchy with small override files.
